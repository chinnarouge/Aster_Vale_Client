WHAT WE'RE BUILDING:
A CLI agent that takes three inputs:
  1. client   — name ("Halden Bet") OR id ("C001")
  2. trigger  — renewal / meeting_prep / upsell / at_risk
  3. rep_context — optional free text from the rep (e.g. "Usage feels down")

The agent orchestrates: an LLM planner decides which tools to call based on
the trigger and rep context, deterministic Python tools gather evidence from
the SQLite database, an LLM writer produces the briefing, and a deterministic
verifier checks every claim.

Output:
  1. A one-page Markdown briefing with cited claims.

IS AN LLM NECESSARY?
Not for calculations. Required only for:
  - Interpreting free-text meeting notes (extracting interests, risks, concerns).
  - Generating natural-language briefing prose from structured evidence.
Everything else (calculations, joins, trend analysis, citations) is deterministic.

RECOMMENDED ARCHITECTURE: Hybrid with LLM Orchestration.
  - LLM planner decides which tools to call based on trigger + rep_context.
  - Deterministic Python tools for all data retrieval and calculations.
  - LLM writer generates the briefing from structured evidence.
  - Deterministic verifier checks citations and numbers.
  - The LLM reasons and writes. Python calculates and verifies.

1. ASSIGNMENT UNDERSTANDING
================================================================================

Aster Vale Sports Data sells sports data products (live feeds, odds, streaming,
widgets, analytics, integrity monitoring) to business clients (sportsbooks,
broadcasters, leagues, clubs, fantasy apps).

Sales reps currently request manual analyst briefings before client interactions.
This takes weeks. We automate it into one-click briefings.

FOUR TRIGGERS:

1. RENEWAL
   - Rep is preparing for contract renewal negotiation.
   - Needs: contract position, ARR history, notice deadline, usage trends
     (growing/declining), overage exposure, support health, competitor signals,
     existing renewal CRM opportunity.
   - Key questions: What should I propose? Where is the risk? What leverage do
     I have? What is the client likely to ask for?

2. MEETING_PREP
   - Rep has an upcoming client meeting.
   - Needs: full account snapshot — who they are, what they buy, how they use
     it, support history, open opportunities, what was discussed last time.
   - Key questions: What do I need to know? What should I bring up? What
     might they bring up?

3. UPSELL
   - Rep wants to grow the account.
   - Needs: products client doesn't hold, segment fit, related products to
     current holdings, existing CRM cross-sell/upsell opportunities, usage
     patterns suggesting capacity for more, interests from meeting notes.
   - Key questions: What should I pitch? Is there evidence they'd want it?
     Is there already an opp in CRM?

4. AT_RISK
   - Rep suspects the client may churn or reduce spend.
   - Needs: declining usage, unresolved P1/P2 tickets, low CSAT, competitor
     mentions in notes, reduced renewal ARR proposals, negative meeting tone,
     stalled opportunities.
   - Key questions: How worried should I be? What signals are there? What
     can I do about it?

MUST-HAVES (from assignment brief):
  M1. Single command: client + trigger -> briefing.md + evidence.json
  M2. Deterministic tools: contract status, usage trends, whitespace,
      support summary, meeting notes
  M3. Trigger-driven planning (config or model, not client-specific code)
  M4. Writer with citations + verifier checking numbers & claims
  M5. Honest data handling: duplicates, gaps, conflicts disclosed
  M6. Evaluation: 3+ clients, 2+ triggers each, automated fact-checks

STRETCH GOALS (do only if time permits):
  S1. Small UI (Streamlit/Gradio)
  S2. Parallel specialists with trace logging
  S3. New trigger via config only
  S4. Meeting note vs data conflict surfacing
  S5. Portfolio view (risk/growth ranking)
  S6. LLM-as-judge scoring
  S7. Unit tests + regression suite

7. ARCHITECTURE COMPARISON
================================================================================

--- Approach A: Fully Deterministic (No LLM) ---

Feasibility: Can handle all calculations, joins, trends, citations.
Limitations:
  - Cannot interpret free-text meeting notes beyond keyword search.
  - Briefing would be template-based: fill-in-the-blanks, robotic.
  - Cannot generate contextual recommendations or nuanced prose.
Verdict: Satisfies most must-haves but produces inferior briefing quality.
         Would not "help a rep" as effectively as natural-language output.

--- Approach B: Hybrid (Deterministic Tools + LLM Writer) ---

Architecture:
  1. Config-driven planner selects tools per trigger.
  2. Deterministic Python tools query SQLite, compute metrics.
  3. Tools return structured JSON with source PKs.
  4. LLM receives tool outputs + meeting note text.
  5. LLM generates briefing with citations.
  6. Deterministic verifier checks citations and numbers.
Strengths:
  - Numbers are always correct (deterministic).
  - Meeting notes can be interpreted in context.
  - Briefing reads naturally and adapts to trigger.
  - Simple to build, test, debug.
LLM hallucination risk (corrected):
  Even when receiving only tool outputs, an LLM CAN still:
  - Misinterpret meeting notes (e.g. infer sentiment not present).
  - Draw unsupported causal connections between data points.
  - Restate numbers incorrectly (e.g. rounding, wrong units, wrong context).
  - Infer unstated facts from patterns in the data.
  Mitigation: The verifier catches numerical errors and missing citations.
  It CANNOT catch misinterpretations of qualitative text. This is a known
  limitation. The system prompt must instruct the LLM to quote meeting notes
  rather than paraphrase, and to flag interpretations as "observation" vs "fact."
LLM is optional:
  The analytical pipeline produces structured JSON evidence independently.
  Without an LLM, a template-based writer can produce a usable briefing:
  - Jinja2 or f-string templates per trigger.
  - Sections populated directly from tool JSON.
  - Meeting notes included as raw quoted text.
  - Recommendations replaced with factual data points.
  This produces a correct but less readable briefing. The LLM improves
  prose quality and note interpretation but is not required for correctness.
Verdict: RECOMMENDED. Best balance of quality, reliability, and simplicity.

--- Approach C: Multi-Agent Architecture ---

Architecture:
  LLM planner -> multiple specialist agents -> LLM synthesiser -> verifier.
Strengths:
  - Most flexible, could handle novel triggers.
  - LLM planner could adapt tool selection dynamically.
Weaknesses:
  - Massively more complex to build in 4-5 hours.
  - LLM planner adds latency, cost, and unpredictability.
  - Config-driven planning is sufficient for 4 known triggers.
  - Harder to test and debug.
  - No clear capability gain over Approach B for this assignment.
Verdict: Over-engineered. Would choose only for a production system with
         dynamic triggers and many more data sources.

COMPARISON TABLE:

Criterion           A: No LLM        B: Hybrid         C: Multi-Agent
Accuracy            High              High              Medium (LLM risk)
Reproducibility     Perfect           High              Medium
Meeting notes       Keyword only      Full interpret.   Full interpret.
Briefing quality    Template/rigid    Natural/adapted   Natural/adapted
Dev time            ~3 hours          ~4-5 hours        ~8+ hours
Testing             Easy              Moderate          Hard
Complexity          Low               Medium            High
Cost per run        $0                ~$0.02-0.05       ~$0.10-0.30
Suitability         Adequate          Best fit          Over-engineered

RECOMMENDATION: Approach B (Hybrid).
The config-driven planner makes LLM planning unnecessary.
The LLM adds value only for meeting-note interpretation and prose generation.

8. EVIDENCE AND VERIFICATION DESIGN
================================================================================

--- Evidence Format ---

Each tool returns a JSON object:

{
  "tool": "get_contract_status",
  "client_id": "C001",
  "timestamp": "2026-11-01T00:00:00",
  "results": {
    "active_contract": {
      "contract_id": "K-0002",
      "start_date": "2025-02-01",
      "end_date": "2027-01-31",
      "arr_eur": 752000,
      "auto_renew": "Y",
      "notice_period_days": 60,
      "notice_deadline": "2026-12-02",
      "days_to_notice": 31,
      "days_to_end": 91,
      "source_rows": ["contracts:K-0002"]
    },
    "previous_contract": {
      "contract_id": "K-0001",
      "arr_eur": 692000,
      "source_rows": ["contracts:K-0001"]
    },
    "arr_change": {
      "value": 60000,
      "pct": 8.67,
      "formula": "(752000 - 692000) / 692000 * 100",
      "source_rows": ["contracts:K-0001", "contracts:K-0002"]
    }
  }
}

--- Citation in Briefing ---

Markdown briefing uses inline citations:

"The current contract (K-0002) has an ARR of EUR 752,000 [contracts:K-0002],
up 8.67% from the previous contract [calc:contract_status.arr_change].
The notice deadline is 2 December 2026 (31 days) [calc:contract_status.notice_deadline]."

--- Verification Rules ---

The verifier is a deterministic Python function that:

1. CITATION CHECK: Every sentence with a number or factual claim must have
   at least one citation in [brackets]. Flag sentences without citations.

2. EVIDENCE EXISTS: Every cited ID must exist in the evidence JSON.
   [contracts:K-0002] -> evidence must contain tool output referencing K-0002.

3. NUMBER MATCH: Every number in the briefing must appear in the cited
   evidence. Match with tolerance for rounding and formatting:
   - "752,000" matches 752000.
   - "8.67%" matches 8.67.
   - Dates match if ISO equivalent.

4. DERIVED METRIC VERIFICATION: For calculated values (percentages, averages,
   changes), verify the formula:
   - ARR change: (new - old) / old * 100.
   - Usage trend: compare period averages using actual monthly values.
   - CSAT average: sum(scores) / count(scores).
   The verifier re-runs the calculation from source values in evidence.

5. UNSUPPORTED CLAIMS: Any claim not traceable to evidence is flagged.

FAILURE POLICY:
  - Missing citation -> Flag in a "verification warnings" section.
  - Number mismatch -> Attempt repair (re-extract from evidence).
    If cannot repair, remove the sentence and note removal.
  - Unsupported claim -> Downgrade to "unverified" with a note.
  - Never silently pass a failed check.

Limitation: Verifying natural-language claims ("the client is unhappy")
against meeting notes is subjective. The verifier checks that the note ID
exists and was for this client, but cannot assess interpretation accuracy.

10. SYSTEM ARCHITECTURE
================================================================================

THREE INPUTS:
  1. client      — "Halden Bet" or "C001" (name or ID, rep types it)
  2. trigger     — renewal / meeting_prep / upsell / at_risk
  3. rep_context — optional free text ("Usage feels down, how worried?")

FLOW:

INPUT: client + trigger + rep_context
  |
  v
[1. RESOLVE CLIENT] ---- Fuzzy match on client_name OR exact on client_id
  |                      "Halden Bet" -> C001, "C009" -> C009
  |                      If ambiguous -> return candidates, stop
  |                      Returns: client_id, client_name, confidence
  v
[2. LLM PLANNER] ------- Receives: trigger, rep_context, available tools list,
  |                      trigger-tool config (which tools are relevant)
  |                      LLM reasons about which tools to call and why
  |                      Returns: ordered list of tools + reasoning
  |                      (Config provides guardrails — LLM can't skip
  |                      REQUIRED tools, can add SECONDARY ones based
  |                      on rep_context)
  v
[3. TOOL EXECUTOR] ----- Python calls each tool from the plan
  |   |                  Each tool: SQL query -> Python calc -> JSON output
  |   |                  All tools are DETERMINISTIC — no LLM inside
  |   |                  Results accumulated in evidence dict
  |   |
  |   +-- get_client_profile     (always first)
  |   +-- get_contract_status
  |   +-- get_usage_trend        (runs per product)
  |   +-- get_whitespace
  |   +-- get_support_summary
  |   +-- get_opportunities
  |   +-- get_meeting_notes
  |   +-- check_data_quality     (always last)
  |
  v
[4. EVIDENCE ASSEMBLY] - Collect all tool outputs into evidence.json
  |                      Assign stable evidence IDs
  |                      Link source row PKs (contracts:K-0002, etc.)
  v
[5. LLM CLAIM GENERATOR] Receives:
  |                      - All structured tool outputs (JSON)
  |                      - Trigger type + rep context
  |                      - System prompt: output structured claims (JSON),
  |                        each with type, value, citations, formula
  |                      LLM outputs an array of structured claims
  |                      Returns: claims[] (JSON, NOT markdown yet)
  v
[6. VERIFIER] ---------- Deterministic Python (NO LLM):
  |                      - Checks each claim against evidence:
  |                        direct_fact: lookup source row, match value
  |                        derived_metric: re-run formula from inputs
  |                        qualitative: confirm cited note exists for client
  |                        recommendation: confirm citations exist, label it
  |                      - Matching rules: normalize money/dates/pct/units
  |                      - Failure policy: flag or remove, never pass silently
  |                      Returns: verified_claims[] + verification_report
  v
[7. RENDERER] ---------- Deterministic Python (NO LLM):
  |                      - Converts verified claims into Markdown briefing
  |                      - Sections ordered by trigger priority
  |                      - Citations inline from claim metadata
  |                      - Data gaps section from check_data_quality output
  |                      Returns: briefing.md
  v
OUTPUT:
  briefing.md              — The rep reads this
  evidence.json            — Tool outputs + structured claims + source PKs
  verification_report.json — What passed, what failed, what was flagged

WHO DOES WHAT:
  LLM: Plans (which tools), writes (briefing prose), interprets (notes)
  Python: Resolves client, executes tools, calculates, verifies, saves
  Rule: LLM never touches the database. LLM never calculates numbers.
        Python never writes prose. Python never interprets meeting notes.

No LangGraph. No vector DB. Plain Python orchestration with LLM calls.

13. RISKS AND LIMITATIONS
================================================================================

1. SYNTHETIC DATA: Patterns may not reflect real-world distributions.
2. MISSING NOTES: 60% of clients have no meeting notes — briefings for
   these clients will lack qualitative context.
3. LLM HALLUCINATION: Writer could invent facts not in evidence.
   Mitigation: verifier catches unsupported numbers; system prompt
   explicitly forbids invention; evidence is the only input.
4. CSAT SPARSITY: 37% of closed tickets have no CSAT. Averages may not
   represent true satisfaction.
5. HISTORICAL CONTRACTS: Only latest expired + current active available.
   Full history unknown for clients with many renewals.
6. SINGLE CURRENCY: All EUR. No currency issues but no multi-currency.
7. STATIC SNAPSHOT: Data frozen at 2026-11-01. No real-time updates.
8. MEETING NOTE SUBJECTIVITY: Notes are one person's interpretation.
   "Tone noticeably cooler" is subjective.
9. NO CLIENT FEEDBACK LOOP: Can't validate whether briefings are useful.

PRODUCTION IMPROVEMENTS (not for this assignment):
  - Live data connections (not static SQLite).
  - User authentication and access control.
  - Briefing feedback mechanism (rep ratings).
  - Incremental updates (not full recalculation).
  - Multi-language support.
  - Audit trail and versioning.
  - Cost monitoring for LLM usage.

15. INTERVIEW PREPARATION
================================================================================

QUESTIONS TO EXPECT AND PREPARE FOR:

Q: Why this architecture?
A: The LLM does what LLMs are good at — reasoning about what to analyse,
   interpreting meeting notes, writing prose. Python does what Python is
   good at — SQL queries, math, verification. Neither does the other's job.
   The trigger config provides guardrails so the LLM planner can't skip
   required tools, but it can reason about emphasis and ordering based on
   the rep's context. Simple enough to build in 4-5 hours, flexible enough
   to handle new triggers and live changes in the interview.

Q: How do you calculate usage trends?
A: Compare average of last 6 months vs prior 6 months. Also compare
   same-month-last-year for seasonal products. Report both absolute and
   percentage change. Flag if <6 months available.

Q: How do you handle the C003 streaming conflict?
A: Report both: data shows decline, note says increase. Present the actual
   monthly series. Note the recent uptick (Aug-Oct) which may partially
   explain the director's perception. Let the rep decide.

Q: Why not calculate a risk score?
A: A single number hides the reasoning. Better to present individual signals
   (declining usage, low CSAT, competitor trial) and let the rep weigh them.
   If forced, would use a weighted checklist, but would explain the weights.

Q: How do you prevent LLM hallucination?
A: Three layers. (1) LLM receives only structured tool outputs — no raw DB
   access. (2) System prompt requires citations for every claim and forbids
   inventing data. (3) Deterministic verifier checks every number and citation.
   Remaining risk: LLM can still misinterpret meeting notes or draw unsupported
   causal connections. The verifier catches numerical errors but cannot assess
   qualitative interpretation accuracy. This is stated as a known limitation.
   Fallback: template-based writer produces correct (if less readable) output
   without any LLM involvement.

Q: How do you handle missing data?
A: Missing row ≠ zero (per data dictionary). Tools detect gaps and report
   them. Briefing includes "data gaps and confidence" section. Trends
   exclude missing months from calculations. Short histories are flagged.

Q: Can you add a 5th trigger?
A: Yes — add an entry to the trigger config dict specifying which tools are
   required/secondary/excluded. The LLM planner already knows how to read
   the config and reason about tool selection. No code changes needed.
   Example: a "contract_gap" trigger that marks contract_status and
   opportunities as REQUIRED, usage as SECONDARY.

Q: How is the verifier independent of the LLM?
A: Pure Python. Parses Markdown for citation patterns, extracts numbers,
   looks them up in evidence JSON. Re-runs formulas for derived metrics.
   No LLM involved. Deterministic. Can be unit-tested.

ADDENDUM A: USAGE TREND METHODOLOGY
================================================================================

Primary measure: Year-over-year (YoY) comparison.
  For each product, compare same calendar months this year vs last year.
  Example for C001 LIVE_DATA:
    Oct 2025: 7433    Oct 2026: 4422   YoY change: -40.5%
    Sep 2025: 8009    Sep 2026: 4883   YoY change: -39.0%
  This controls for seasonality.

Secondary measure: Recent 3-month momentum.
  Average of most recent 3 months vs previous 3 months.
  Example for C001 LIVE_DATA:
    Recent 3 (Aug-Oct 2026): avg(4962, 4883, 4422) = 4756
    Prior 3 (May-Jul 2026): avg(6382, 5112, 4299) = 5264
    Momentum: -9.7%

Handling incomplete history:
  - <6 months: Report absolute values only. Flag "insufficient history for
    trend analysis" in data gaps section. Do not calculate YoY.
  - 6-11 months: Calculate momentum only. No YoY.
  - 12+ months: Calculate both YoY and momentum.

Handling missing months:
  - Skip missing months from averages. Do not impute.
  - Report the gap: "2026-03 data unavailable, excluded from trend."
  - If >2 consecutive months missing, flag unreliable trend.

Never interpret missing usage as zero consumption.

ADDENDUM B: OVERAGE ESTIMATION
================================================================================

Overage = max(0, units_used - included_units_monthly) for each month.
Estimated charge = overage_units * overage_rate_eur_per_unit.

CRITICAL: Use the contract line and rate applicable to that specific month.
  - Match each usage month to the contract in force during that month
    using: month >= contract.start_date AND month <= contract.end_date.
  - Then match the product to the contract line for that contract.
  - Use THAT line's included_units_monthly and overage_rate_eur_per_unit.

If no signed contract covers a usage month (e.g. pending_signature or gap),
the overage estimate cannot be calculated for that month. Report this.

The usage_monthly table already has an included_units column which records
the included volume from the contract in force that month. Where available,
this is the most reliable source. Where blank, no signed contract covered
the month.

Clearly label all overage figures as ESTIMATED. These are calculated from
usage vs contract terms, not actual invoiced amounts.

ADDENDUM C: IMPROVED VERIFICATION DESIGN
================================================================================

STRUCTURED CLAIMS (canonical writer flow):

The writer does NOT go straight to Markdown. It follows three steps:
  Step 1: LLM generates structured claims (JSON array).
  Step 2: Verifier checks each claim against evidence (deterministic).
  Step 3: Renderer converts verified claims into Markdown briefing.

Claims are stored in evidence.json alongside tool outputs. The verification
report records what passed, failed, was flagged, or was removed.

This means: Markdown is a rendered VIEW of verified claims, not raw LLM text.

Each claim is a structured object:

{
  "claim_id": "CL-001",
  "type": "direct_fact",           // direct_fact | derived_metric | qualitative | recommendation
  "statement": "Current ARR is EUR 752,000",
  "value": 752000,
  "citations": ["contracts:K-0002"],
  "verification": "lookup"         // lookup | formula | note_reference | unverifiable
}

{
  "claim_id": "CL-002",
  "type": "derived_metric",
  "statement": "ARR increased 8.67% at last renewal",
  "value": 8.67,
  "citations": ["contracts:K-0001", "contracts:K-0002"],
  "formula": "(752000 - 692000) / 692000 * 100",
  "inputs": {"old": 692000, "new": 752000},
  "verification": "formula"
}

{
  "claim_id": "CL-003",
  "type": "qualitative",
  "statement": "Client tone was noticeably cooler in June meeting",
  "citations": ["note:N-002"],
  "verification": "note_reference"
}

{
  "claim_id": "CL-004",
  "type": "recommendation",
  "statement": "Consider offering a reduced in-play scope to retain the account",
  "citations": ["note:N-003", "opp:O-0001"],
  "verification": "unverifiable"   // recommendations cannot be fact-checked
}

VERIFICATION BY CLAIM TYPE:
  direct_fact:     Look up cited source row, verify value matches.
  derived_metric:  Re-run formula from inputs, verify result matches value.
  qualitative:     Verify cited note exists and belongs to this client.
                   CANNOT verify interpretation accuracy. State this.
  recommendation:  Verify citations exist. Cannot verify correctness.
                   Flag as "recommendation, not factual claim."

VERIFIER MATCHING RULES BY DATA TYPE:
  Monetary: "EUR 752,000" matches 752000. Ignore currency prefix, commas.
  Percentage: "8.67%" matches 8.67. Allow ±0.1 for rounding.
  Dates: "2 December 2026" matches "2026-12-02". Parse both to date objects.
  Units: "8,000 API calls" matches 8000. Strip unit labels before comparing.
  Counts: "5 P1 tickets" — verify 5 matches the count in evidence.
  Derived: Re-run formula from stored inputs. Allow ±0.5% for rounding.
  Recommendations: NOT verifiable as fact. Must be labeled type=recommendation
    with supporting citations. Verifier confirms citations exist, does not
    assess whether the recommendation is correct.

LIMITATION: A deterministic verifier cannot assess whether "tone was cooler"
is a reasonable interpretation of meeting note N-002. It can only confirm
that N-002 exists, belongs to C001, and was dated 2026-06-12. Interpretation
accuracy requires human review or LLM-as-judge (stretch goal).

Recommendations that the LLM invents without supporting citations must be
flagged and removed. The LLM can only recommend based on evidence it was
given (e.g. "consider WIDGETS" is valid if whitespace tool shows segment
fit + related product held; "consider expanding to Asia" has no evidence).

ADDENDUM D: CONFIDENCE VS URGENCY
================================================================================

Confidence and urgency are independent dimensions.

CONFIDENCE = How reliable is our evidence?
  HIGH:   Signed contract, 12+ months usage, CSAT from 10+ tickets.
  MEDIUM: Pending contract, 6-11 months usage, partial CSAT data.
  LOW:    No contract, <6 months usage, no CSAT, no meeting notes.

URGENCY = How time-sensitive is the finding?
  HIGH:   Notice deadline passed or <30 days. Contract gap. Open P1 ticket.
  MEDIUM: Notice deadline 30-90 days. Active renewal negotiation.
  LOW:    Contract end >6 months. No immediate deadline.

Example: C007 (Varrow Racing Authority)
  Confidence in contract info: LOW (no active contract, pending_signature).
  Urgency: HIGH (contract gap exists NOW, service continuity at risk).
  -> The briefing should say: "HIGH URGENCY: No active contract in force.
     K-0045 awaiting signature. Evidence confidence for contract terms: LOW
     (terms not yet finalised)."

Example: C004 (Quillon Esports)
  Confidence in usage trends: LOW (only 2 months of data).
  Urgency: LOW (new 12-month contract, 10 months remaining).
  -> "Usage trend analysis unavailable: insufficient history (2 months)."
